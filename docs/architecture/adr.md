## ADR-001 自研引擎的长期维护策略

**状态**：Proposed · **决策人**：主理人 · **日期**：2026-11（W3）

### 背景

- 引擎为自研 HTML5+WebGL2+JS，零 import/export、全局变量耦合、103 模块按
  pack 顺序注入（pack1→4 顺序不可变，见 module-map §一）。
- 已上线第一赛季（B 站 Toy 独占），线上有真实玩家与天梯/云存档/账号资产。
- 代码库整体质量**高于典型"玩具引擎"**：FramePacer/DynRes/区块预算/毒区块
  重启/guard 子系统隔离/分帧存档/多标签页仲裁（Instances）——健壮性设计是
  自研的、成体系的，迁移引擎将全部丢弃或重写。
- 维护痛点集中于：①全局耦合与 monkey-patch 链（net.js 6 层 onMessage 包装、
  potato.js 对 Game/UI/Player 的运行时改写）；②两个巨石（potato.js 562KB、
  game.js 218KB）；③`self.XZ` 对局引擎不在源码树。
- 团队正在用"源码树还原 + 增量新模块"演进（W5b 陀螺仪即新模块路径）。

### 备选方案

**A. 维持自研引擎 + 架构内改良（本 ADR 倾向）**
**B. 迁移 PlayCanvas / Three.js 系（同为 WebGL，浏览器原生）**
**C. 迁移 Godot 4（Web 导出）**

### 决策

**倾向 A：长期维持自研引擎，但以"三条护栏"约束增量开发**；不立项引擎迁移。
具体护栏：

1. **新代码一律新模块**（如 w5b 陀螺仪），禁止往 potato.js/game.js 追加
   顶层逻辑；接入点只能用 patch 包装（现有惯例）且 patch 必须集中登记。
2. **冻结 pack 顺序语义**：任何新全局不得与现有全局重名（CI 加 acorn 扫描，
   tools/ 已有 pack-order.json 可扩展校验）。
3. **巨石只读化**：potato.js/game.js 进入"只改 bug、不进新特性"状态；
   新 UI 走独立 HTML 层模块（PotatoShare 已示范该模式）。

### 理由

- 迁移成本估算（关键论据）：
  - B：玩法主体（potato.js 第一赛季全部射击玩法/大厅）**不可搬运**——
    它直接 patch 游戏原型链；估算全量重写 ≥3 人月，且 B 站 Toy iframe
    环境（postMessage RPC、审核、包体限制）适配风险未知。
  - C：Godot Web 导出二进制 ≥30MB、SharedArrayBuffer/跨域隔离要求与
    Toy 容器兼容性未知；GDScript 重写全部玩法 ≥6 人月；体素网格/光照
    管线（chunk_worker/mesher/shaders）需要完全重做。收益（编辑器、场景
    系统）对这个"玩法全在代码里"的项目利用率低。
  - A 的沉没资产恰好是竞品最难复刻的部分：8 周冒烟打磨出的性能预算体系、
    worker 降级链、B 站平台适配（toy.js 的 mock/回退/容错极厚）。
- 风险对冲：A 并非"永不迁移"，而是把迁移前置条件写明——见"后果"第 4 条。

### 后果

1. 短期（本季度）：开发速度不损失；W5b 等增量任务照常。
2. 中期代价：全局耦合继续累积，新人上手成本上升（依赖 module-map 与
   本架构文档缓解）；monkey-patch 链长度需监控（建议登记表 + pack 顺序
   断言，超 8 层强制拆模块）。
3. 测试策略必须适配全局架构：以浏览器级冒烟（longRun/PerfMon 采集）为主，
   单元测试只能覆盖纯函数模块（util/mesher 数学部分等）。
4. **迁移触发条件（写入护栏）**：若出现以下任一，重开本 ADR——
   ① Toy 平台政策变化导致 WebGL2 不可用；② 需要原生 App/主机端；
   ③ 单帧预算体系无法支撑赛季玩法的实体规模（p99 >2×目标持续两周且
   DynRes 已到底）。

### 替代方案被否原因

- B（PlayCanvas）：仅解决渲染层，而渲染层是本引擎最稳的部分；代价却是
  玩法全重写——收益倒挂。
- C（Godot 4）：见"理由"；另有 Toy 容器兼容未知风险，需先做 2 周 spike
  才值得谈，当前无此人力信号。

## ADR-002 对局网络架构演进（排位赛权威服务器）

**状态**：Proposed · **决策人**：主理人 · **日期**：2026-11（W3）

### 背景

- 现状三条通道（network-protocols.md §〇）：rooms（WS，服务器权威世界，
  但输入/容器/物品预测在客户端）、p2p（房主权威 + AntiCheat 校验）、
  **对局引擎 XZ（1V1/2V2 Bo5/淘汰赛/约战）= 源码树外的黑盒**。
- 天梯带 Elo/段位/赛季资产 → 有作弊经济价值；而反作弊现状（architecture.md
  §三）：移动/伤害校验只存在于 P2P 房主端，rooms 模式信任客户端 tick 报文；
  `_t` token 明文 body；无报文签名。
- 服务器已有真实权威服务（rooms 的世界模拟在服务端，proxy 提示语证实
  存在 `multiplayer/proxy` 服务端仓库），具备扩展对局权威的基础。
- 前端已实现 `ReconnectScreen`（extras.js）但未接线；断线即退赛。

### 备选方案

**A. 排位赛迁到 rooms 式专用权威服务器（每场对局=一个临时 rooms 房间，
  服务端跑完整世界模拟 + 服务端裁决伤害/移动）**
**B. 保持现状（XZ 黑盒 + 客户端信任），仅把 AntiCheat 的 p2pHit/p2pState
  校验逻辑移植到权威端**
**C. 折中：服务器权威"轻世界"——对局只加载竞技场区块+玩家实体，
  服务端校验位置/伤害/命中，外观同步沿用现有报文**

### 决策

**倾向 C（轻权威），分两步走**：

- **第一步（低风险，1~2 周级）**：把 anticheat.js 的 p2pHit 距离/攻速/伤害
  上限公式与 p2pState 移动规则**移植到服务端**（rooms 与对局通道都启用），
  并给 `_t` 加 HMAC 报文签名（对 `t/pos/attack` 类关键字段）。
- **第二步（赛季 S2 前）**：对局专用轻权威进程（每场对局一个 arena 实例，
  预算上 rooms 已证明服务端可承载房间世界模拟），落库走 /api/ladder。
- 排位赛**需要**专用权威：理由是 Elo 资产 + 客户端信任盲区（物品栏
  `click.changed` 可伪造、tick 位置可信度无校验）二者的组合风险随赛季
  奖励上升而放大。

### 理由

- A（全量 rooms 复用）最省事但浪费：对局不需要完整世界（红石/村民/
  容器全无用），服务端负载会限匹配容量。
- B 不解决根因：校验仍在客户端对端（rooms 模式下对端= 服务器吗？——
  现状 rooms 模式根本没有校验执行点，必须新增服务端执行点，B 的表述
  实际滑向 C）。
- C 与现有代码兼容性最好：客户端已按"服务器权威"分支编写（netTick），
  服务端只需校验而不必重算全部物理；p2p 的 AntiCheat 公式是现成的、
  经过实战调参的规则库。
- XZ 黑盒是本决策的**前置缺口**：在拿到 XZ/服务端仓库前，第一步的落地
  点只能是 rooms/p2p 通道，对局通道的服务端改造需主理人先补齐源码或文档。

### 后果

1. 服务端工程量：第一步 ≈ 规则移植 + 签名（1 人 1~2 周）；第二步
   arena 实例管理 + Elo 落库（估 2~4 人周，视服务端仓库现状）。
2. 客户端几乎零改动（校验在服务端），但误封率需灰度：先只 flag 不 kick，
   用 telemetry("ac") 数据调阈值（现有 30s 节流上报可直接复用）。
3. 网络延迟敏感度上升：服务器权威裁决意味着 hit/移动在服务端确认，
   NET_DELAY=110ms 的插值口径要与新裁决时延联合调参。
4. 断线重连成为对局刚需：接通 ReconnectScreen（extras）或对局内
   "重进=继续 Bo5 当前局"，否则权威化反而放大掉线判负的挫败。
5. 非排位玩法（乱斗/人机/靶场）可维持现状，避免全量改造。

### 替代方案被否原因

- A：容量/成本不匹配（完整世界模拟跑对局纯属浪费）。
- 维持纯现状：天梯经济价值 vs 零服务端校验的组合不可持续；第一赛季
  玩家基数尚小时是窗口期，S2 奖励上线前必须完成第一步。

## ADR-003 build 产物维护策略（还原代码的长期演进）

**状态**：Proposed · **决策人**：主理人 · **日期**：2026-11（W3）

### 背景

- 源码树来自 build 产物还原：prettier 格式化、**变量名 terser 级压缩不可恢复**，
  仅"结构级可维护"（module-map §五）。
- 已完成：103 模块拆分、pack-order.json、tools/build.mjs 重建链、
  W0 冒烟 + 8812 冒烟（longRun CSV 可作性能回归基准）。
- 双人并行开发现实：W5b 正在改 src（写面互斥由此任务铁律体现）。

### 备选方案

**A. 增量新模块（新功能 = 新文件 + patch 接入），旧巨石只修不进**
**B. 逐模块重写（每次接触一个模块就重写成可读命名 + 模块化，测试覆盖后替换）**
**C. 全量重写（按 architecture.md 分层在新代码库重建）**

### 决策

**倾向 A（增量新模块）为主，B 作为"被动机会主义"补充**：

1. 一切新特性、新系统、平台层改动 → 新模块（已由 ADR-001 护栏 1 确立）。
2. **重写触发条件**（满足才允许 B，且一次只一个模块）：
   a. 该模块本季度有 ≥2 次需求变更（反复打开 = 回本）；
   b. 模块体积 <40KB 且对外暴露的全局 ≤10（net.js/game.js/potato.js 量级
      的模块明确排除）；
   c. 有 W0 冒烟 + 新写的特征测试可作替换安全网。
3. 重写的验收标准固定：`tools/build.mjs` 重建产物与原 pack 顺序兼容、
   8812 冒烟全绿、longRun CSV 性能指标不劣化（fps p50/p95、heapMB）。
4. 永不改：blockdata/itemdata/entitydata 等纯数据巨石（无维护收益，
   只有回归风险）；只建立"数据补丁层"（新模块覆盖式注入）做数据修正。

### 理由

- B 的单价被变量名不可恢复严重抬高：重写 = 重新理解语义（读行为）+
  重新命名 + 全量回归，而收益只是"这个模块好读了"。对低变更频率模块，
  回本周期超过剩余赛季生命周期。
- C 的风险在第一赛季运营期不可接受：potato.js 里的玩法语义（对局规则、
  枪械数值、签到/股东活动）没有任何设计文档，全量重写等于二次逆向 +
  高概率引入不可察觉的行为漂移（数值/时序）。等 ADR-001 的迁移触发
  条件命中时，C 会自然并入该决策。
- A 的已知风险（全局命名膨胀、patch 链变长）已由 ADR-001 护栏 2/3 与
  "登记表"机制对冲。

### 后果

1. 代码库将长期呈现"还原体 + 新模块圈层"的双层结构；新人指南必须
   明示这个事实（本文件 + architecture.md 即为入口）。
2. patch 接入点需要登记表（建议 `docs/architecture/patch-registry.md`，
   W5b 之后的任务补建）：模块名 / 被包装的原型方法 / 顺序 / 作用。
   现 onMessage 已 6 层包装，超 8 层强制新模块化。
3. 测试资产成为 B 的前置投资：把 8812 冒烟固化为可重复 CI 冒烟
   （longRun 5 分钟档 + PerfMon 阈值断言）优先级应高于任何重写计划。
4. 数据修正走补丁层意味着 blockdata 的真相分散在两处——补丁层必须
   集中单一文件并记录来源，禁止散落各模块内 patch。

### 替代方案被否原因

- B 全量推进：单价/回本不成立（见理由 1）；仅在触发条件下局部采用。
- C：运营期风险不可控，且与 ADR-001 维持自研的决策重复建设。
