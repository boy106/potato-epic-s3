# POTATO EPIC 热修与回滚流程

## 1. 基本策略

客户端是纯静态包，但没有源码、CI、版本管理，当前文件名又稳定复用。最大风险是：**非原子覆盖叠加 HTTP 缓存/`force-cache`，让同一会话混用新旧 index、pack、worker 或 mod；回滚后也可能继续读到缓存中的坏包。**

目标架构：

1. 每次发布生成不可变目录 `releases/<BUILD>/`，包含全部静态文件、逐文件清单与完整包 SHA-256。
2. 候选在独立预览地址验收，公开入口通过一次性指针/软链接切换。
3. 若 B站 Toy 不支持目录切换，使用平台等效原子发布；上传资源后再最后更新入口仍只是次优方案，必须证明不会混包。
4. 至少保留当前版、上一稳定版和一个更早已知良好版的只读归档；归档不能只存在生产服务器上。

禁止直接在线改单个 JS、只回滚一个 pack、或同版本号覆盖文件。

## 2. 热修准入与审批

适用：大面积无法启动/进房、存档或奖励数据风险、安全漏洞、严重错误平衡、明确法务/平台风险。普通体验优化走日常迭代。

热修可以缩短等待时间，但不能省略：

- 用户/发布负责人明确批准，记录严重度、影响范围和预期修复；
- 新 `BUILD`、最小差异、针对性 QA、完整资源清单、后端兼容、回滚包；
- 上线后验证、玩家沟通与完整时间线。

涉及存档、账号、经济或奖励时，后端/数据负责人必须共同批准。任何“先上线再补验证”均为 NO-GO，除非用户明确接受风险且不存在数据/安全 Blocker。

## 3. 热修步骤

### T0：止血与定界（0–10 分钟）

1. 建立 incident ID，指定唯一现场负责人，记录首个异常时间、版本、设备与后端状态。
2. 保全 telemetry、integrity、404/JS error、rooms/pm 与玩家反馈证据；不要先清日志。
3. 判断立即动作：关闭相关 live 活动/入口、公告降级、直接回滚，或允许继续热修。
4. 若正在扩大数据损坏、安全风险或大面积不可用，优先回滚，不等待完美修复。

### T1：制备候选

1. 从“当前线上包的只读归档”建立工作副本，不从个人目录或缓存取基线。
2. 代码负责人只做最小修复；资源变化同时更新对应 mod 版本与清单。
3. 分配新版本：同日 `a→b`，跨日新日期从 `a` 开始；同步启动页、补丁说明和包名。
4. 重新生成全部文件的字节数/完整 SHA-256，核对差异仅限批准范围。

### T2：验证与发布

1. 在全新浏览器配置跑启动、核心对局、mod、workers、云存档与后端冒烟；另用已访问旧版的浏览器验证升级。
2. 检查 telemetry 收到新 `BUILD`，integrity 脚本集合与基线一致，无意外外部/内联脚本。
3. 备份当前公开指针，原子切换到候选，执行缓存失效。
4. 用真实 Toy 容器复验，而非只查文件上传成功；观察约定窗口后再关闭事故。
5. 发布热修公告，归档审批、差异、测试证据、缓存动作、上线时间与结果。

## 4. 回滚步骤

1. **宣布回滚**：记录触发条件、批准人、目标稳定 `BUILD`；必要时暂停相关 live/news/签到活动。
2. **兼容检查**：确认 rooms/pm、协议、live 配置、云存档与排行榜支持旧客户端。若不支持，不得单独回滚前端。
3. **验证归档**：重新解压上一稳定包，核对完整包哈希和逐文件清单，确认它是完整产品而非残片。
4. **整体切换**：原子恢复整个静态目录/公开指针；不能只换 `index.html` 或一个 pack。
5. **处理缓存**：刷新 CDN/平台缓存并验证响应头；必要时短期将入口设为 `no-store`。浏览器已有缓存无法被服务器强行清空。
6. **双会话验证**：新会话与曾使用坏版本的会话均显示目标 `BUILD`，网络请求无跨版本混包，后端/telemetry/integrity 正常。
7. **数据与沟通**：检查云存档冲突、活动状态和奖励；向玩家说明已回退版本、影响与反馈入口。
8. **复盘**：坏包继续隔离保留用于分析，不再作为回滚源；后续修复基于明确代码状态并分配新版本。

## 5. 缓存失效注意事项

### 当前代码实证

- `index.html` 用 `fetch(location.href,{cache:'force-cache'})` 统计脚本标签；旧入口可能给出错误的加载计数。
- `js/integrity.js` 对 index 和脚本使用 `force-cache`，上报的是浏览器实际取到的内容，不保证是服务器最新内容。
- `mods/index.json` 与 mod 下载使用 `no-cache`，这是重新验证而非绝对绕过缓存；live 使用 `no-store`。
- 未发现 Service Worker 注册；不要凭空把问题归因于 SW，也不要执行不存在的 SW 清理步骤。

### 推荐响应策略

| 资源 | 当前同名发布模式下建议 |
|---|---|
| `index.html` | `Cache-Control: no-cache, must-revalidate`；事故期可短期 `no-store` |
| `mods/index.json` | `no-cache, must-revalidate`，确保版本/size/files 可重新验证 |
| 同名 `pack*.js`、独立 JS、mod 代码与资源 | 在内容寻址改造前使用 `no-cache`；不要配长期 `immutable` |
| 带内容哈希或位于不可变版本目录的资源 | 才使用长期 `max-age` + `immutable` |

注意：

- 简单给 script URL 加 `?v=BUILD` 不足以自动解决全部问题：integrity 的 `rel()` 会移除 query，随后按无 query 路径 `force-cache` 重新取文件。任何 cache-busting 改造都要同步检查 worker、动态 mod 和 integrity。
- 不依赖“玩家强制刷新”作为唯一方案；B站 WebView/Toy 容器与 CDN 都可能保留旧响应。
- 不让玩家清除站点数据来升级，这可能影响 localStorage 设置和 IndexedDB 本地存档。
- 观察 `GAME_BUILD` 与 integrity 哈希分布；同一公开版本出现多套非预期哈希时按混包事故处理。

## 6. 完整性与遥测边界

- 当前 integrity 对 SHA-256 只取前 8 字节（16 个十六进制字符），且是上报机制，不是本地白名单或强制阻断。发布归档必须另存**完整 SHA-256**。
- 对 index 的上报哈希有 Toy 注入脚本归一化逻辑；比对基线时必须使用相同算法，不能直接拿原始文件哈希对比该字段。
- telemetry 在 localhost/部分内网地址默认关闭，所以本地静态服务器测试不能证明线上上报正常；需在生产或等效 HTTPS 环境验证后端实际落库。

## 7. 后端与数据不可自动回滚

静态包回滚不会撤销：账号变更、云存档 revision、签到领取、新闻、live 配置、股东名单、天梯结果或后端协议变更。

- 后端有独立备份和迁移回滚方案时，按独立审批执行。
- 禁止为配合客户端回滚而直接恢复整库或删除新存档；先评估增量合并、兼容层或只读降级。
- 若旧客户端会误读新数据，必须保持新客户端或启用后端兼容层，不能强行回退。

## 8. 完成定义

热修/回滚只有在以下证据齐全后才关闭：目标版本唯一可见、无混包、核心路径通过、后端与云存档稳定、遥测恢复、公告发布、审批与时间线归档。当前尚未做实切/回滚演练，因此本流程是**已建立、未演练**，不能标为已验证能力。
