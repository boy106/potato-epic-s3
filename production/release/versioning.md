# POTATO EPIC 版本号规范

- 负责人：路远行（发布运营）
- 适用范围：B站 Toy 静态客户端、mod、补丁说明、遥测与回滚包
- 当前实证：`js/pack4.js` 内 `GAME_BUILD="2026.11.14a"`；`index.html` 展示 `BUILD 2026.11`
- 原则：**任何已发布字节发生变化，都必须使用新版本号；版本号永不复用。**

## 1. 两层版本标识

### 1.1 客户端唯一技术版本 `BUILD`

沿用现有格式，避免破坏 telemetry、integrity 和玩家设置中的版本记录：

```text
YYYY.MM.DD<rev>
示例：2026.11.14a
```

| 部分 | 含义 | 规则 |
|---|---|---|
| `YYYY.MM.DD` | 发布日期 | 以 Asia/Shanghai 的计划上线日期为准；月份、日期保留两位；跨日后首次发布使用新日期 |
| `rev` | 当日修订字母 | 当日首个候选为 `a`，之后依次为 `b`、`c`；仅使用小写 ASCII 字母 |

`2026` 是年份，**不是主版本号**。不要把现有日期格式解释为 SemVer，也不要省略修订字母。

### 1.2 产品主版本 / 赛季版本

对外完整名称采用：

```text
S<赛季号> · <BUILD>
示例：S1 · 2026.11.14a
```

- 当前产品主版本为 **S1（第一赛季）**；赛季号是产品与运营主版本，不塞进 `BUILD`，以免影响既有上报字段。
- 赛季切换由内容、经济和运营计划决定，不因日期跨月或普通热修而变化。
- 赛季切换不重置日期或修订字母；例如 S2 首个版本可以是 `S2 · 2026.12.01a`。
- 存档结构、网络协议或后端不兼容变更必须另记 `save_revision` / `api_compatibility`，不能用“赛季变了”代替兼容性说明。

## 2. 何时递增

| 情况 | 新版本规则 | 示例 |
|---|---|---|
| 当日首次常规迭代 | 新日期或当日首个修订 | `2026.11.14a` |
| 同日再次发布，含内容、平衡或资源变化 | 修订字母 +1 | `2026.11.14b` |
| 同日 hotfix | 修订字母 +1 | `2026.11.14a` → `2026.11.14b` |
| 跨日 hotfix | 使用新日期并从 `a` 开始 | `2026.11.15a` |
| 上传失败但从未对外可见的候选 | 可继续使用该候选号；一旦进入公开环境即不可复用 | — |
| 仅重新压缩、改名或替换一个音频，字节有变化 | 仍递增 | `a` → `b` |
| 只改后端公告且客户端包不变 | `BUILD` 不变；记录后端/live 配置版本 | — |

禁止“同号覆盖”。同号覆盖会使缓存、integrity 哈希、问题报告和回滚审计失去可靠边界。

## 3. Hotfix 编号与补丁说明

- Hotfix 没有另一套特殊后缀，直接使用下一个 `BUILD`；这样玩家、遥测和回滚只需识别一个版本。
- 补丁说明标题写 `S1 · 2026.11.14b 热修公告`，正文明确“修复自 `2026.11.14a` 起出现的问题”。
- 从旧版本回滚时沿用旧包的原 `BUILD`，不得伪造一个新字母来伪装旧内容；公告写“已回退至……”。
- 回滚后的再次修复必须基于实际代码状态分配一个新版本，并在记录中写明 `supersedes` / `rolls_back_to`。

## 4. 启动页展示一致性

### 当前缺口

`index.html` 的 `BUILD 2026.11` 只是静态字样，与真实 `2026.11.14a` 不一致。它会误导玩家反馈、客服排障和发布核验。

### 目标方案（交代码负责人实施）

1. `GAME_BUILD` 是唯一事实源。
2. 启动页设置独立节点，例如 `<span id="build-number">BUILD …</span>`。
3. 在 `pack4.js` 加载后，由启动脚本将节点更新为 `BUILD ${GAME_BUILD}`；脚本加载失败时保留通用 `BUILD` 字样，不展示伪造旧版本。
4. 补丁说明、发布记录、压缩包文件名和遥测中的 `build` 均引用同一值。

### 过渡期强制门控

在单源改造完成前，每次发布必须同时检查：

- `GAME_BUILD` 符合 `YYYY.MM.DD[a-z]`，且全包只有一个赋值事实源；
- `index.html` 展示完整版本，不仅显示到月份；
- 补丁说明、压缩包名、发布记录中的版本完全一致；
- 遥测收到的新会话 `build` 等于候选版本。

## 5. Mod、后端与客户端版本的关系

- `mods/index.json` 内每个 mod 有独立版本，当前为 `xzguns=1.0`、`xzrange=1.0.0`。它们不替代客户端 `BUILD`。
- 任一 mod 的 `data/code/bundle/tiles/sounds` 发生变化时，递增该 mod 版本，并同步重新生成 `files`、`size` 与发布哈希。
- 建议 mod 后续统一为 SemVer `MAJOR.MINOR.PATCH`；现有 `1.0` 不在无变更发布中强行改写。
- 客户端发布记录必须写明后端地址、协议兼容范围和云端配置版本。纯前端回滚不会自动回滚 rooms/pm、live、news、checkin 或 cloudsave。

